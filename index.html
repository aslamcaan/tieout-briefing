tieout: filed accounts, checked by code

tieout reads UK company accounts filed at Companies House and writes a standardised Excel workbook and a one-page summary. Code reads every figure and checks every figure it can. Each figure carries its source and a status, so a reviewer knows which numbers to trust and which to check.

Built by Aslam. Measured on 696 held-out filings through a logged final command.

Why I built it

Analysts copy company accounts into spreadsheets by hand before they can compare or model them. Software vendors put a manual spread at 30 minutes to several hours per borrower, depending on scope. These are the vendors' claims, not measurements.

The harder problem is trust. A typed-in figure looks the same whether it is right or wrong, so a reviewer cannot tell which numbers to check.

What it changes

  • The PDF reader took 0.9 seconds per filing on the test split, with no model.
  • Every figure carries its source (file, page or tag, exact text) and a status, so review starts at the flagged figures.
  • On the test split, read from PDFs rendered from tagged filings (cleaner than most filed PDFs), 0.2% of core values were wrong and not flagged.
  • It helps credit analysts, private equity and corporate finance associates, and anyone screening UK private companies. A person still reviews the output; that review time was not measured.

How it works

Code decides, the model proposes. A language model may suggest what an unfamiliar PDF row label means. It never does arithmetic, never decides pass or fail and never writes output text.

  1. Read tagged iXBRL accounts (Tier 1), PDF accounts by page layout (Tier 2), or scans through OCR (Tier 3).
  2. Map each line to a canonical item by dictionary, fuzzy match or, optionally, a model suggestion.
  3. Check the arithmetic: totals tie, signs make sense, periods line up.
  4. Mark every figure with a status and its provenance.
  5. Write the workbook and the one-pager.

Every figure has a status

VERIFIEDMatched its source text and passed an arithmetic cross-check. Not the same as audited. UNVERIFIEDRead from the filing; no check could confirm it. FLAGGEDA check failed. Shown with the sum and the difference, and kept out of the ratios. n/dNot disclosed, by a written rule. Never shown as zero. missingThe filing shows the line but it could not be read.

How it was tested

  • Companies split into train, validation and test by a hash of the company number, fixed before any tuning.
  • The test split run only through a logged command, twice on the same sample, with no tuning on it.
  • Planted errors (digit swaps, scale and sign errors) to measure what the checks catch.
  • Real scanned filings scored separately against labels, and every validation PDF read again as a degraded scan.
  • A second held-out set of 505 filings from October 2026, weighted to full and group accounts and run once: 0.5% of core values wrong and not flagged.
  • Every number in the docs and on this page filled in from the report files by script.

Hindsight case: Patisserie Holdings

The café chain announced potentially fraudulent accounting irregularities in October 2018, including in its cash. tieout read its scanned accounts from before the collapse.

  • In the last accounts before the collapse, revenue was £114.2m (VERIFIED) and cash £21.5m (VERIFIED). Every check that applied passed.
  • Nothing fired that points at the problem. A misstated figure that adds up passes arithmetic checks, so VERIFIED never means true.
  • Where tieout's own reading went wrong (a scale change in one year, and at first the comparable Greggs' six-column income statements), the checks caught it and flagged the figures instead of using them. The reader now reads each year's total column on such statements.

Limits

  • The main test reads PDFs rendered from tagged filings, which are cleaner than most filed PDFs. Read as degraded scans, the rate rises to 1.0% (95% CI 0.6% to 1.6%, n = 4,676), above the target.
  • Most test filings are micro and small companies. The test bucket held only 36 group and 60 full accounts.
  • Figures the filer did not tag cannot be scored by tags. Counting those as errors when unflagged, the rate is 9.5%; of a sample of 200 of them checked against the printed accounts, 198 were right (checked by a model, not a person).
  • Full accounts have an upper bound of 1.8% on 60 filings, above the target.
  • Arithmetic checks cannot catch false numbers that add up. tieout does not detect fraud.

Questions people ask

Does it detect fraud?

No. Arithmetic checks cannot catch false numbers that add up. A separate screen marks figures "worth a closer look", such as cash that earns little interest or debtors growing faster than revenue. It fires on ordinary companies too, and it never says fraud.

Does a model make up any numbers?

No. Code reads, adds up and checks every figure. A model may suggest what an unfamiliar row label means, and that fallback is off by default. It never does arithmetic, never decides pass or fail and never writes output text.

What does VERIFIED mean?

The figure matched its source text and passed an arithmetic cross-check. It does not mean audited or true.

Which filings can it read?

Tagged iXBRL accounts, PDF accounts with a text layer and scanned PDFs through OCR. Scans are the slowest and the least reliable, and the output says so figure by figure.

Does it read US companies?

Yes, listed companies that file a 10-K with the SEC. Their accounts are tagged, so tieout reads the tags through a US-GAAP concept map and runs the same checks. On a random sample of 60 SEC filers it read 38; the rest were foreign filers, funds or companies with no 10-K yet. Borrowings are not read from US filings yet, and the outputs say so.

How were the results measured?

Companies were split into train, validation and test sets by a hash of the company number before any tuning. The test set was run only through a logged command and never tuned on. Every number on this page is filled in from the report files by script.
